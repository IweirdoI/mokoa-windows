## 二、问题 1：Markdown 依赖已加入 `package.json`，但 `pnpm-lock.yaml` 未同步

### 证据

- `frontend/package.json` 已声明两个 Markdown 渲染依赖：

  ```
  "dependencies": { "dompurify": "^3.4.15", "marked": "^18.0.13", "vue": "^3.5.13" }
  ```

- `frontend/pnpm-lock.yaml` 的 `importers..dependencies` **只有 `vue`**，`packages`/`snapshots` 段
  亦无 `marked`、`dompurify` 任何条目 —— 锁文件与 `package.json` 不一致。
- `frontend/package-lock.json`（npm）**已同步**：含 `dompurify@3.4.15`、`marked@18.0.13`。
- 引入提交定位：`00378d8 feat(frontend): 流式 markdown 实时渲染（rAF 合并 + XSS 消毒）`
  改动文件为：

  ```
  frontend/package-lock.json | 1397 +++++++++++++++++
  frontend/package.json      |    2 +-
  frontend/src/main.js       |   53 +-
  frontend/src/style.css     |   13 +
  ```

  即该提交只更新了 npm 的 `package-lock.json`，**未更新 `pnpm-lock.yaml`**。
- `frontend/pnpm-workspace.yaml` 存在（`packages: ["."]`），说明该工程按 pnpm 组织。

### 影响

- 在评审/CI 环境执行 `pnpm install --frozen-lockfile` 会报
  `ERR_PNPM_OUTDATED_LOCKFILE`（lockfile 与 `package.json` 不同步）而失败。
- 若执行不带 `--frozen-lockfile` 的 `pnpm install`，会就地改写 `pnpm-lock.yaml`，产生未提交脏变更。
- 同时存在 npm 与 pnpm 两套锁文件，包管理器不唯一：`frontend/README.md` 指导使用 `npm install`，
  而 `pnpm-workspace.yaml` 又表明 pnpm。评审方用哪种方式安装会得到不同结果。

### 建议

- 二选一统一包管理器；若沿用 pnpm，则在 `frontend/` 下执行 `pnpm install` 重新生成并提交
  `pnpm-lock.yaml`（使其包含 `marked`、`dompurify`），或移除 `pnpm-workspace.yaml` 并明确只用 npm。
- 不要把 `frontend/dist/` 纳入提交（当前 `git ls-files frontend/dist` 为空，符合预期，勿回退）。

## 三、问题 2：后端开启鉴权后，前端请求未携带令牌

### 证据

- 后端 `api/server.py:99-116`：当环境变量 `API_AUTH_TOKEN` 非空时启用鉴权中间件；
  除 `/health` 外全部端点必须携带 `Authorization: Bearer <token>`，否则返回 401。
- 前端 `frontend/src/ingestion.js:71-90` 的 `requestApi()`：

  ```js
  const headers = new Headers(options.headers)
  if (!(options.body instanceof FormData) && options.body != null && !headers.has('Content-Type'))
    headers.set('Content-Type', 'application/json')
  const response = await fetch(`/api${path}`, { ...options, headers, signal: controller.signal })
  ```

  仅设置 `Content-Type`，**未注入 `Authorization`**。
- 前端 `frontend/src/main.js:261-300` 的 `streamChat()` 直接 `fetch('/api/agent/chat/stream', ...)`，
  请求头同样只有 `Content-Type`，**未注入 `Authorization`**。
- 后端已有针对性测试 `tests/test_api.py:380 test_api_requires_token_when_configured`；
  前端测试 `frontend/tests/ingestion.test.js` 未覆盖令牌注入路径。

### 影响（实际故障链路）

1. 顶栏「连接 API」调用 `/health` —— 该端点被豁免，**能通过**，界面显示"实时 API 已连接"；
2. 随后 `loadDashboard()` 调 `/stats/*`、`/preferences/*`、`/preferences/*/profile` —— 全部 401；
3. 发送对话走 `/agent/chat/stream` —— 401；遗忘 `/forget`、接入 `/ingest`、`/ingest/file` —— 全部 401。

即：**开启鉴权后前端"看起来连上了、实际全挂"**，属于易被误判的静默失败。
（注意 Vite 代理 `frontend/vite.config.js` 只做 `/api` 转发与重写，不会自动附加该请求头。）

### 建议

- 前端统一从 `import.meta.env.VITE_API_TOKEN` 读取令牌，在两处出口（`requestApi` 与 `streamChat`）
  统一注入 `Authorization: Bearer <token>`；令牌为空时保持向后兼容（本地开发不配置即不带）。
- 后端 CORS 已 `allow_headers=["*"]`，无需额外放行该头。
- SSE 使用 `fetch` + `ReadableStream`（非 `EventSource`），可正常携带自定义请求头，无需改用查询参数传令牌。
- 建议在 `frontend/tests/ingestion.test.js` 增加"配置令牌时请求头包含 `Authorization`"的断言。

**C. 误报提示（不算残留，勿误改）**

- `src/preference/keys.py:41` 的 `"C:/Users/{user}/Downloads"` 是模板占位符 `{user}`，非个人用户名。

### 影响

- 交付/评审材料中出现成员本机用户名与主机名，属于个人信息泄露，与既往匿名化工作
  （`0c3bd32 refactor(anonymization)`、`5bfb38c fix(security)`）的目标不一致 ——
  前两轮只脱敏了成员姓名，**未覆盖本机用户名、主机名与绝对路径**。
- 部分位于 `scripts/` 的硬编码主机名会直接报错阻断：非 `<kylin-host>` 机器执行相关验收脚本会
  主动 `fail`/`exit`，即脚本在他人机器上不可复用，同时暴露命名信息。

### 建议

- 文案类（`.md`）：把 `/home/<user>/projects/MOKOA/...` 改为仓库相对路径或 `<repo>/...` 占位；

- 脚本类：`scripts/kylin_v11_*.py|sh`、`scripts/eval_kylin_scale_recall.sh` 不应硬编码具体主机名，
  建议改为环境变量（如 `KYLIN_HOST`）或校验"是否 Linux + 是否 Kylin"的能力探测，而非等值比较主机名。
- 证据类 JSON（`docs/evidence/**`）：把 `path`/`dataset` 字段中的绝对路径替换为相对路径或占位，
  必要时在生成脚本里统一做路径归一化，避免下次复跑再次写入本机路径。
- 测试 `tests/test_local_llm_pref.py:8`：删除写死的 `sys.path.insert`，改用
  `Path(__file__).resolve().parents[1]` 动态加入仓库根（也修复了他人机器上必然导入失败的问题）。
- 建议补一个匿名化自检脚本/CI 钩子（只匹配“用户目录路径”这类模式，避免把具体主机名固化进仓库）：
  `git grep -n -i -E "[A-Za-z]:[\\/]+Users|/home/[A-Za-z]|/Users/[A-Za-z]"`，命中即失败；
  主机名类残留建议在本地用已知主机名临时比对，不要写入仓库。
