# Windows BGE-M3 赛题验收报告

验收日期：2026-09-05。基线：`71740b5`，本轮包含下述本地小修复。对照依据：仓库 `赛题.md`，XA-202612。

## 结论

**Windows + 真实 BGE-M3 主链可以运行，但尚未完整达到赛题要求。** 多源接入、偏好版本与跨场景、记忆晋升、常规脱敏和自然语言遗忘已实跑；热模型检索延迟在本机千条规模下符合 500 ms 要求。长期库持久化、入口安全一致性、知识冲突更新、偏好提取质量和聊天到偏好面板的流程仍有缺口。

仅将银河麒麟原生 SDK、麒麟系统兼容性和真机适配报告列为本轮不适用。**持久化、安全、知识冲突和评测质量不能因 Windows 系统而豁免。** 本轮不构成麒麟 SDK 或 Milvus 真机验收。

## 已修复的小问题

1. **实时模式混入演示内容**：连接成功和切换用户时，清空演示记忆、旧聊天、活动、偏好及遗忘结果；异步面板响应不再回填到另一个用户。请求执行期间禁用用户与连接切换。
2. **拒收被显示为写入成功**：前端检查 `accepted`，显示质量拒绝原因；无召回时的助理文案也根据实际写入结果生成。
3. **非法参数导致 500**：`/recall`、短期与中期列表采用枚举校验；`top_k` 限制为 1–100，错误请求返回 422。

修改文件：`frontend/src/main.js`、`api/server.py`。新增 6 个参数校验测试和 4 个可重复执行的 Windows 验收脚本。

验证：初始全量回归 **294 passed**；修改后的 API 与新增校验测试 **18 passed**；前端构建通过；Edge 无头浏览器 **7/7 检查通过**，覆盖演示内容清理、真实拒收文案、无浏览器异常、点击遗忘和切换用户清空聊天。真实 API 经 Vite 代理调用返回成功。

一次初始“控制字符清洗”检查将接收成功也作为条件，因正常质量拒收被误记失败。响应正文实际上已清除控制字符。最终脚本将清洗与质量门分开断言，未修改清洗规则。

## 待负责人处理的问题

### P1：长期记忆随后端重建丢失

- 建议负责人：cb0aeabe（存储）+ efca9634（工厂与部署）。
- 复现：默认内存后端写入 20 条长期知识，再新建同类型后端查询同一用户，结果为空。
- 影响：SQLite staging 只是审计中转，不等同于权威长期库恢复。不能按“系统不同”豁免。
- 验收建议：明确 Windows 可用的持久化部署；同一库关闭服务后重开，确认知识、偏好版本、删除状态均一致，重新测真实存储延迟。

### P1：查询过滤参数能覆盖用户范围

- 建议负责人：efca9634 + cb0aeabe，2abac5a6参与安全边界审查。
- 复现：`POST /recall`，请求 `user_id="boundary_other"`，`filters={"user_id":"win_retrieval"}`，可返回后者知识。
- 位置：`orchestrator.recall()` 更新调用方 filters；`query_memory()` 合并 filters 时允许覆盖 user_id。
- 影响：即使暂不接身份认证，接口中的用户范围也自相矛盾；后续账号接入不能仅信任客户端 user_id。
- 验收建议：把用户范围绑定到可信上下文，禁止 filters 覆盖；覆盖查询、按 ID 查询、写入和遗忘入口的用户隔离测试。本轮只操作合成测试用户。

### P1：直接入库入口绕过脱敏

- 建议负责人：2abac5a6 + efca9634，cb0aeabe配合存储约束。
- 复现：`POST /store-entry` 写入合成测试手机号 `13800138000`，`memory_type=document_chunk`、`source=manual`；随后 `/recall` 返回原文。
- 对比：同一手机号经 `/ingest` 会形成 HASH 占位符。
- 影响：不同写入入口没有统一安全保证，不能整体宣称“敏感信息已过滤”。后续自然语言遗忘在该样例中可删除，但不能抵消之前明文可召回的问题。
- 验收建议：统一可信入库边界，对直接 entry、偏好提取、晋升和更新分别补全脱敏与索引一致性检查。

### P1：知识冲突未统一处理

- 建议负责人：efca9634 + cb0aeabe。
- 复现：同一用户、同一 `metadata.record_key="help_service_port"`，依次直接写入“端口为8080”和“已改为9090、旧端口不再使用”，随后知识召回仍返回两条。
- 位置：`store_memory_entry()` 无 preference_key 时直接创建；`resolve_knowledge()` 的实体级融合仍未实现。
- 影响：旧事实与新事实同时用于回答；现有偏好冲突 6/6 不足以证明赛题知识冲突正确率≥88%。
- 验收建议：建立实体/属性/场景身份、版本与失效策略，给知识冲突单独设置标注集，包含替换、兼容并存和不可确定情况。

### P2：聊天输入偏好不进入长期画像，面板流程未闭合

## 复现与证据

在项目根目录使用已装依赖的 Python，开两个终端：

```powershell
# 终端1：新建隔离证据目录；模型缓存必须已存在
$env:PYTHONIOENCODING='utf-8'
python scripts/windows_bge_acceptance.py --out data/evidence/windows_bge_repeat --serve
```

```powershell
# 终端2：边界与规模测试，目标固定为隔离的18085端口
python scripts/windows_boundary_acceptance.py data/evidence/windows_bge_repeat/boundary
python scripts/windows_scale_acceptance.py data/evidence/windows_bge_repeat/scale

# 启动前端（可在第三个终端运行）
cd frontend
$env:VITE_API_TARGET='http://127.0.0.1:18085'
npm.cmd run dev -- --host 127.0.0.1 --port 5178 --strictPort
```

浏览器脚本从项目根执行 `node scripts/windows_frontend_acceptance.cjs <输出目录>`。需要安装 Playwright 与 Edge，或用 `PLAYWRIGHT_MODULE` 指向现有 Playwright 模块目录。本轮使用 Codex 自带的 Playwright 及本机 Edge，没有新增项目依赖。

原始证据相对根目录：

- `data/evidence/windows_bge_2026-09-05/final-http/acceptance.json`：模型信息、47 项断言、所有主流程 HTTP 请求/响应、40条查询排名及延迟、资源快照。
- `data/evidence/windows_bge_2026-09-05/boundary-final/boundary.json`：5 项边界结果和完整请求。
- `data/evidence/windows_bge_2026-09-05/scale/scale.json`：100/1000条规模每次请求延迟。
- `data/evidence/windows_bge_2026-09-05/preference-rule.json`：35条样本逐条期望、预测与错漏。
