# 流式输出流畅度分析（2026-09-14）

## 结论摘要

MOKOA 的流式对话"不流畅"并不是网络或协议问题，而是**后端在 token 推送链路中插入了一层多余的"节流批量冲刷"（`_TokenThrottle`）**，把模型本应"逐 token 实时"的输出切成了 20–90ms 的批次，视觉上表现为"停顿—涌出—停顿—涌出"。更关键的是，该节流器的**动态调参逻辑是反效果的**：模型产出越快（尤其是本地 LM Studio），刷新间隔反而被拉大、每批字符更多，顿挫感越明显。

次要因素还包括：首 token 前的同步开销（大 prompt 拼接 + 全量脱敏）、以及"同步模型流 + 跨线程队列"架构本可直接逐 token emit 却被节流器隔断。前端为纯文本渲染（无 markdown 实时解析的 O(n) 重渲染问题），但每个事件都触发 `scrollToBottom()`，长回答下存在滚动微抖风险。

---

## 端到端数据流链路

```
模型 token 流 (complete_stream, 同步生成器, worker 线程)
   │ 每收到一个 chunk
   ▼
_emit_token(text)                         service.py:967
   │ 交给节流器
   ▼
_TokenThrottle.push(text)                 service.py:885   ← 入 buffer
   │ 后台线程每 interval 秒(默认45ms, 动态20-90ms)刷一次
   ▼
_TokenThrottle._run → _emit({type:token}) service.py:899  ← 人为批次延迟在这里产生
   │
   ▼
_event_queue.put(event)                    service.py:962  (普通 queue.Queue)
   │
   ▼
chat_stream: loop.run_in_executor(None, queue.get)   service.py:1220  (异步取)
   │
   ▼
yield "data: {json}\n\n"                   service.py:1221  (SSE)
   │
   ▼

     + 每事件 scrollToBottom()             frontend/src/main.js:324 / 154
```

**问题点**：token 并非到达即推，而是先进入 `_TokenThrottle` 的 buffer，必须等后台定时线程（每 20–90ms）唤醒后才 `_emit` 进队列。这一层缓冲对"流畅度"是毁灭性的，且对"降低开销"几乎没有收益。

## 根因逐条

### 根因 1（首要）：`_TokenThrottle` 节流器制造人为批次延迟

`src/agent/service.py` 中 `_TokenThrottle` 的设计是"攒批后定时冲刷"：

```python
866:928:src/agent/service.py
class _TokenThrottle:
    def __init__(self, emit, min_ms=20.0, max_ms=90.0, base_ms=45.0, max_buffer=240):
        ...
        self._interval = base_ms / 1000.0   # 默认 45ms
    def push(self, text):
        with self._lock:
            self._buf.append(text)          # token 先进 buffer
            self._size += len(text)
            ...
            if self._size >= self._max_buffer:   # 240 字符才强制刷
                ...
                self._emit(...)
    def _run(self):
        while not self._stop:
            time.sleep(self._interval)      # 定时线程：每隔 interval 刷一次
            with self._lock:
                if self._buf:
                    self._emit({"type": "token", "text": chunk})
            # 动态调整 interval ...
```

- token 不直接进 SSE 队列，而是先入 buffer，后台线程每 `interval` 秒（默认 45ms，可调 20–90ms）才冲刷一次。
- 无论模型多快，用户看到的最小粒度都是"每 20–90ms 涌出一段字符"，而非逐字流动。
- 这是"不流畅"的最直接来源。

### 根因 2（加重）：动态调参方向反了 —— 模型越快越卡顿

`_TokenThrottle._run` 末尾的动态调整逻辑：

```python
908:915:src/agent/service.py
            rate = self._produced / self._interval
            low, high = 60.0, 600.0  # 字符/秒
            norm = (rate - low) / (high - low)
            norm = 0.0 if norm < 0 else (1.0 if norm > 1 else norm)
            ideal = self._min + (self._max - self._min) * norm
            self._interval = self._interval + 0.3 * (ideal - self._interval)
```

- 注释意图："负载低（产出慢）时把分度调小以保持响应，负载高（产出快）时调大以批量降低开销"。
- 实际效果：**本地模型产出越快（rate 越高），`norm`→1，`ideal`→`_max`(90ms)，`interval` 被拉大**，于是每批字符更多、刷新间隔更长 → 顿挫更明显。
- 即出现"本地 LM Studio 越快越卡"的反直觉现象，恰恰与"流畅"目标相悖。

### 根因 3：节流器的"降低 SSE 开销"前提不成立

- 注释把节流器动机写为"降低服务端开销 / 批量降低开销"。但 SSE 每个事件只是写一行 `data: {...}\n\n`，`uvicorn` 是流式分块写入，单事件开销极小。
- "高频小请求"的担忧属于 HTTP 连接层，逐 token 推送 SSE 并不会增加连接数或显著 CPU 开销。节流器把 HTTP 层的考量错误地套用到了 SSE event 层，是过度设计。

### 根因 4：架构本可"逐 token 实时 emit"，却被节流器隔断

- `complete_stream` 是**同步生成器**（`httpx.Client` 同步 + `OpenAI` 同步），运行在 `_run_stream_graph` 的后台线程（`MemoryAgent.__init__` 编译好 `StateGraph`，`chat_stream` 起线程跑它）。
- 该 worker 线程本可在每收到一个 chunk 时**直接** `self._emit({"type": "token", "text": piece})` 进 `queue`，由 `chat_stream` 的 `loop.run_in_executor(None, queue.get)` 实时 yield 出去，实现真正逐 token 流式。
- 但 `_model` 节点选择走 `_emit_token` → `_TokenThrottle.push`，把"实时 emit"改成了"定时批量 emit"，多绕了一层完全多余的缓冲。

```python
1052:1060:src/agent/service.py
        if self.streaming:
            raw = None
            for chunk in self.model.complete_stream(messages, tools or None):
                if chunk["kind"] == "token":
                    self._emit_token(chunk["text"])   # ← 进节流器，而非直接 _emit
                elif chunk["kind"] == "message":
                    raw = chunk["message"]
```

### 根因 5（次要）：首 token 前的同步开销造成"开流迟滞"

在第一个 token 到达前，以下同步工作在 worker 线程完成：

- `recall` 阶段：`json.dumps({"memories":..., "preferences":...}, ...)[:16000]` 拼接大上下文，并 `redact_sensitive_text(context[:16000])` 脱敏（`service.py:980`、`989`）。
- `_model` 阶段：`protect()` 递归对**全部 messages**（含上面 16000 字符历史 + 记忆）做脱敏/占位符映射（`service.py:1020` 起）。
- 向量检索 `self.memory.recall(...)`（`service.py:958`）。

这些步骤不产出任何 token 事件，用户看到的是"发送后停顿一会儿才开始出字"。本地快模型下整体仍偏快，但大 prompt 拼接 + 全量脱敏会放大这段空白。

### 根因 6（前端次要）：每个事件都触发 `scrollToBottom()`

```javascript
296:297:frontend/src/main.js
          if (event.type === 'token') {
            ensureMsg(); assistantMsg.content += event.text
...
324:frontend/src/main.js
          scrollToBottom()   // 每个事件（含每个 token 批次）都调一次
```

```javascript
154:157:frontend/src/main.js
    const scrollToBottom = async () => {
      await nextTick()
      if (chatScroll.value) chatScroll.value.scrollTop = chatScroll.value.scrollHeight
    }
```

- 前端是纯文本渲染（`<div class="bubble">{{ message.content }}</div>`，`main.js:460`），**没有** markdown 实时解析的 O(n) 重渲染问题，这点反而比多数实现好。
- 但每个 token 事件都 `await nextTick()` + 读 `scrollHeight` + 设 `scrollTop`。当前端更新频率被后端节流器限制在 20–90ms 时问题不大；**一旦去掉后端节流器、改为逐 token 推送，前端需要相应加入 `requestAnimationFrame` 合并渲染/滚动的兜底**，否则高频纯文本更新在长回答下也可能掉帧、滚动抖动。

### 根因 7（并发层，非单条流畅度）：`run_in_executor(None, queue.get)` 占用线程池

- `chat_stream` 用 `loop.run_in_executor(None, self._event_queue.get)` 阻塞等待队列（`service.py:1220`）。默认线程池 `max_workers = min(32, cpu+4)`。
- 每个 SSE 连接长期占用一个线程池线程。多用户同时流式时可能挤占默认线程池，间接影响其他协程/请求调度。单条对话"不流畅"与此无关，但高并发下值得关注（可改用 `asyncio.Queue` + `await queue.get()` 彻底异步化）。

## 改进方向（供参考，未实施）

1. **删除/弱化 `_TokenThrottle`**：`_model` 流式分支直接 `self._emit({"type": "token", "text": piece})`，让 token 实时进队列 → 实时 SSE。若担心极端高频，可改为"仅按 buffer 上限（如 240 字符）强制刷、不引入定时线程"，或直接去掉节流。
2. **排队结构异步化**：把 `queue.Queue` 换成 `asyncio.Queue`，`chat_stream` 用 `await self._event_queue.get()`，避免 `run_in_executor` 占用线程池。
3. **首 token 优化**：`recall` 与 `protect` 的 16000 字符拼接/脱敏可评估是否必须全量入 prompt，或改为流式脱敏、按需裁剪历史，缩短"开流迟滞"。
4. **前端合并渲染**：去掉后端节流后，在 `handlers` 中把 token 累积到一个本地缓冲，用 `requestAnimationFrame` 周期性地把缓冲刷到 `assistantMsg.content`，并将 `scrollToBottom` 改为 rAF 节流，避免逐 token 触发 `nextTick` + 滚动。

## 验证方式

- 去掉节流器后，用浏览器开发者工具 Network 面板观察 `/api/agent/chat/stream` 的 `data:` 事件间隔：应呈现连续、细粒度（接近逐 token / 每十几毫秒）的推送，而非 20–90ms 的成批涌出。
- 主观对照：本地 LM Studio 快模型下，回答应从"一段段蹦字"变为"连续滚动"，且长回答不出现明显停顿。
- 回归：确认 `done` 事件仍在所有 `token` 之后到达（顺序正确性由 `_run_stream_graph` 在图执行完毕后才 `put(done)` 保证）。
