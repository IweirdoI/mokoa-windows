## 复查范围与方法

- 信任边界：外部 HTTP 请求 → `api/server.py` → `MemoryOrchestrator` → 存储/检索/LLM。
- 方法：人工走查 API 端点、上传/抓取工具、出站与密钥处理、全局错误处理、依赖清单。
- 环境：本地 OS Agent，主要为 localhost 部署；生产部署时以下多数问题暴露面会显著放大。

## 发现项

### #1 API 缺少鉴权 + CORS 配置过宽（Critical）

- 位置：`api/server.py` 全部端点、`CORS` 配置（行 66–72）。
- 问题：
  1. 所有端点（`/ingest`、`/ingest/file`、`/agent/chat`、`/recall`、`/forget`、
     `/stats/{user_id}`、`/short-term/{user_id}`、`/mid-term/{user_id}`、
     `/preferences/{user_id}`、`/consolidate/{user_id}`、`/store-entry`、
     `/staging/purge`、`/staging/stats` 等）**均无身份认证/授权**。
     任意能访问端口的客户端可读写、删除任意用户的记忆（`/forget`、`/staging/purge`
     为破坏性操作）。
  2. CORS：`allow_origins=["*"]` 且 `allow_credentials=True` 是无效且不安全的组合
     （浏览器会拒绝，且语义上等价于任意源带凭证）。
- 修复方向：
  - 鉴权：新增**可选** Bearer Token 中间件，由环境变量 `API_AUTH_TOKEN` 开启；未配置时
    保持本地开发兼容（不破坏既有前端/脚本），配置后强制校验 `Authorization: Bearer`。
  - CORS：`allow_origins` 改为由 `API_CORS_ORIGINS` 配置（默认仅 localhost 列表），
    `allow_credentials` 仅在显式配置非 `*` 来源时才允许。

### #5 Web 抓取工具存在 SSRF 缺口（High）

- 位置：`src/agent/service.py:_web_fetch`（行 592–617）。
- 问题：该函数对任意 `http/https` URL 直接 `urllib.request.urlopen`，**未做 SSRF 防护**。
  攻击者/恶意指令可令 Agent 抓取 `http://169.254.169.254/`（云元数据）、
  `http://10.0.0.1/admin`、`http://127.0.0.1:port` 等内网与本地服务，造成内网探测或
  凭据泄露。
- 已存在但未复用：`src/security/outbound.py:is_loopback_service` 仅允许回环，且
  `semantic_detector`/`vision` 的 LLM 端点已用其限制；web fetch 未调用任何出站守卫。
- 修复方向：在 `outbound.py` 新增 `is_external_url_safe`（放行公网、阻断私有/回环/链路本地/
  元数据地址），并在 `_web_fetch` 入口强制校验；同时保留已有的长度与读取字节上限。

### #6 文件上传缺少分块大小兜底 + 解压炸弹残留风险（High）

- 位置：`api/server.py:/ingest/file`（行 266–304）、`src/ingestion/file_extract.py`。
- 问题：
  1. `data = await file.read()` 将**整个上传体读入内存**。防御中间件（Batch D）仅基于
     `Content-Length` 头做 50MB 上限判断；若为分块传输（无 `Content-Length` 头），该守卫
     **被跳过**，超大文件会在到达 `extract_document` 的 8MB 内部检查之前耗尽内存（OOM DoS）。
  2. `extract_document` 内部 `MAX_FILE_BYTES=8MB` 上限约束了 `.docx` 解压炸弹的压缩前体积，
     但 `python-docx`/`pypdf` 对解压后体积无额外限制，理论上 8MB 压缩包仍可膨胀消耗大量内存。
- 已确认安全：`file_extract` 仅用 `Path(filename).name` 取基名作为元数据，**不**用文件名
  拼接任何磁盘路径，无路径穿越风险。
- 修复方向：在 `/ingest/file` 中以**有界分块读取**（累计超过 `MAX_FILE_BODY_BYTES` 即拒），
  保证无论是否带 `Content-Length` 都不会无限占用内存；解压炸弹风险以 8MB 上限为已知约束并记录。

### #9 缺少统一全局异常处理（Medium）

- 位置：`api/server.py`（仅 `SemanticDetectionUnavailable`/`MemoryBackendUnavailable` 有
  自定义处理器；其余异常走框架默认）。
- 问题：未捕获的运行时异常由框架返回 500。当前 `debug=False`（默认）下不回显堆栈，但
  个别端点用 `detail=str(exc)`（如 `ModelUnavailable`）可能把内部信息透出；且缺乏统一的
  错误结构与日志，不利于排障与告警。
- 修复方向：注册全局 `Exception` 处理器，返回不含内部细节的通用 500；保留已注册的 503 处理器；
  确保业务异常的消息经脱敏后透出。

### #10 `/health` 端点信息泄露（Medium）

- 位置：`api/server.py:/health`（行 184–218）。
- 问题：在验收模式下回显 `os.getpid()`、`OS_AGENT_ACCEPTANCE_RUN_ID`、`collection`、
  `vector_dim`、`MEMORY_VECTOR_DIM` 等环境变量与进程信息。虽为只读状态，但在多租户/暴露部署
  下会泄露内部拓扑与版本细节，辅助攻击者 reconnaissance。
- 修复方向：仅返回非敏感的 `status` 与基础能力标识；移除原始环境变量回显（验收专用字段可
  置于独立受控端点或仅在 `debug` 显式开启时返回）。

### #11 依赖未锁定，供应链可复现性弱（Low/Medium）

- 位置：`requirements.txt`。
- 问题：多数依赖使用 `>=` 下限（如 `pydantic>=2.0`、`fastapi>=0.110`、`pymilvus>=2.4.0,<3.0`、
  `openai>=1.30`），仅 `langgraph==1.2.11` 锁定。新环境 `pip install` 可能拉取到非预期的新版本，
  引入行为差异或已投毒版本，且难以复现评审环境。
- 修复方向：将安全/接口敏感依赖锁定到当前验证通过的版本（`==`）；CI 增加 `pip check` 与
  锁定文件（如 `requirements.lock`/`pip-tools`）。**注意**：直接改 `requirements.txt` 可能
  影响已验证的 `.venv`，建议作为独立评审项推进，不在本轮强制改动。

## 已确认安全（非问题，记录以免重复审查）

- `exec_terminal`（`service.py`）：使用 `AGENT_EXEC_ALLOWED_COMMANDS` 命令白名单 +
  沙箱根目录 + 超时 + 输出截断，无 shell、无任意命令执行。
- `semantic_detector` / `vision`：LLM 端点经 `is_loopback_service` 限制为回环地址。
- `protect_payload`（`outbound.py`）：出站载荷按密钥字段脱敏，禁止未脱敏附件外发。
- `file_extract`：文件名仅取 basename 作元数据，无路径穿越。
- 审计/原始归档：Batch G 已改用语义级脱敏（#8）。
