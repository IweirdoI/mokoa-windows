## 一、短期记忆是什么？

短期记忆（Short-term Memory）是记忆生命周期的**第一层**，对应赛题要求 **(6) 短/中/长期记忆流转** 中的「短期」阶段。

作用可以概括为：

- 接收经过 ingestion 清洗、Orchestrator 分类后的**新鲜记忆**
- 在**会话级、进程内**暂存，容量有限（默认每用户 10 条）
- 为后续的**中期晋升 → 长期入库（Milvus）** 做缓冲和筛选

**重要边界：**

| 短期记忆**是** | 短期记忆**不是** |
|-------------|----------------|
| 写入后的第一站（staging/working memory） | 最终持久化库（知识检索模块：cb0aeabe - Milvus） |
| 按 `user_id` 隔离的内存队列 | 向量检索的主数据源（RAG 走 Milvus） |
| 带 heat 的热度池，供晋升中期用 | 偏好版本化的最终存储（偏好记忆模块：26a9835a + Milvus） |

```
│  第 1 步  多源接入模块（3fba60e1） ingestion                       │
│           原始 JSON → 清洗/标准化/质量评估 → NormalizedRecord    │

                             ▼
┌─────────────────────────────────────────────────────────────────┐

│           安全过滤 → 分类(偏好/知识) → short_term.write()        │
│                              ← 【短期记忆在这里】                │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│  第 3 步  偏好记忆模块（26a9835a） preference（并行/后续）           │
│           从 NormalizedRecord 提取偏好 → MemoryEntry              │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│  第 4 步  编排核心模块（efca9634） consolidate                     │
│           短期 → 中期(heat达标) → 长期 → resolve_and_store       │
└────────────────────────────┬────────────────────────────────────┘
                             ▼

│  第 5 步  知识检索模块（cb0aeabe） Milvus create_memory / query_memory │

```

**一句话：短期记忆 = 数据流第 2 步的落点；第 4 步才离开短期、走向 Milvus。**

## 四、技术设计要点

### 4.1 存储方式

- **当前：进程内内存 dict**（服务重启后清空）
- **未来可选：短期/中期记忆独立持久化**（需单独设计；3fba60e1 SQLite staging 仅负责 ingestion 审计与 TTL 去重，不复用为记忆层存储）

### 4.2 容量与淘汰

- 每用户独立队列，默认容量 **10 条**（`configs/default.yaml` → `memory.short_term_capacity`）
- 超出容量时 **FIFO 淘汰最早一条**，返回 `evicted_memory_id` 供审计
- `read_short()` 与短期查询 API 默认按创建时间 **最新优先** 返回；读取顺序不改变 FIFO 淘汰规则

### 4.3 去重与更新（fingerprint）

- 使用多源接入模块（3fba60e1）ingestion 产出的 **`metadata.fingerprint`**（SHA-256）
- 同一用户、相同 fingerprint 再次写入 → **原地更新**，不新增条目
- 更新时：`version + 1`，`access_count + 1`，`updated_existing = true`

> 注意：ingestion 层有 TTL 去重（5 分钟窗口），短期层有 fingerprint 合并，两层逻辑不同、互补。

### 4.4 热度 heat（为中期晋升准备）

```
heat = access_count + quality_score + confidence × 0.5
```

- `access_count`：写入/访问次数
- `quality_score`：ingestion 质量分
- `confidence`：来源置信度

当 `heat >= mid_term_heat_threshold`（默认 **5.0**）时，`promote_to_mid()` 可将其升入中期。

### 4.5 分类（写入时打标）

Orchestrator 在写入短期前调用 `classifier.py`，给每条记忆打：

- `memory_type = "preference"` — 用户偏好
- `memory_type = "knowledge"` — 领域知识/工具经验

分类依据：关键词 + `record.type` + `metadata`（如 `config_key`、`tool_name` 等）。

## 五、中期记忆（Mid-term）

### 5.1 定位

中期记忆是 **heat 达标后** 从短期晋升的「高价值片段池」：

- 默认容量 **50 条** / 用户（`memory.mid_term_capacity`）
- 进程内内存，服务重启清空（与短期相同）
- 是 `consolidate()` 中 **mid → long → Milvus** 的缓冲层

### 5.2 晋升规则（short → mid）

1. 短期条目的 `heat >= mid_term_heat_threshold`（默认 **5.0**）
2. `POST /consolidate/{user_id}/mid` 或完整 `POST /consolidate/{user_id}` 触发
3. 达标条目从短期移出，写入中期池

### 5.3 相似度去重（mid 写入时）

配置项：`memory.mid_term_similarity_threshold`（默认 **0.7**）

写入中期时，若与池内已有条目满足以下任一条件，则 **合并** 而非新增：

| 条件 | 行为 |
|------|------|
| 相同 `record_key` / `fingerprint`（身份键） | 强制合并，`version + 1` |
| 相同 `memory_type` 且文本相似度 ≥ 0.7 | 合并，保留 quality 更高者的 content |

合并后：`access_count + 1`，`heat` 重算，`metadata.mid_merged = true`。

### 5.4 晋升长期（mid → Milvus）

`promote_to_long()` 规则：

- 扫描中期桶全部条目
- `quality_score >= quality_threshold`（默认 0.6）→ 先进入 **`_long` 待入库队列**
- 未达标 → **保留在中期**，等待下次 consolidate

**持久化（权威长期 = Milvus，cb0aeabe `create_memory`）：**

```
consolidate()
  → promote_to_long()        # 写入 _long 待入库队列
  → resolve_and_store()      # 调 create_memory / store_memory_entry
  → release_long_pending()   # Milvus 成功后从 _long 移除
```

| 层级 | 存储 | 含义 |
|------|------|------|
| `_long` | 进程内队列 | **待入库**，consolidate 成功后应为 0 |
| **Milvus** | cb0aeabe memory_service | **权威长期记忆**，RAG 走 `/recall` |

入库失败（如 `memory_policy` 拒绝）时，条目**保留在 `_long`**，下次 consolidate 可重试。

### 5.5 代码文件

| 文件 | 职责 |
|------|------|
| `src/core/mid_term.py` | `MidTermMemory`：容量、FIFO、相似度合并 |
| `src/core/layer_manager.py` | `promote_to_mid` / `promote_to_long` / `read_mid` |

## 六、写入后的 MemoryItem 结构（短期/中期通用）

每条短期记忆是一个 `MemoryItem`：

| 字段 | 说明 |
|------|------|
| `id` | UUID，短期记忆唯一 ID |
| `memory_type` | `preference` / `knowledge` |
| `layer` | 固定为 `short` / `mid` / `long` |
| `content` | 记忆正文（embedding 只用这个字段） |
| `user_id` | 用户 ID |
| `scene_id` | 场景 ID（可空，跨场景偏好用） |
| `version` | 版本号，fingerprint 更新时递增 |
| `metadata` | 见下表 |

**metadata 关键字段（下游需关注）：**

| 字段 | 来源 | 用途 |
|------|------|------|
| `fingerprint` | 多源接入模块（3fba60e1）cleaner | 短期去重、冲突识别 |
| `quality_score` | 多源接入模块（3fba60e1）quality | heat 计算、晋升参考 |
| `source_type` | Orchestrator | `behavior`/`tool_result`/`manual_config`/`conversation` |
| `confidence` | ingestion | heat 计算 |
| `config_key` / `preference_key` | 多源接入模块（3fba60e1）normalizer + Orchestrator | 偏好识别、冲突 key |
| `access_count` / `heat` | 短期记忆模块 | 中期晋升 |

### 7.1 写入短期记忆：`POST /ingest`

前端 / Agent 通过此接口写入；**成功即进入短期记忆**。

**请求：**

```json
{
  "user_id": "demo_user",
  "source": "manual_config",
  "scene_id": "coding-session",
  "payload": {
    "key": "reply_language",
    "value": "中文",
    "confidence": 0.8
  }
}
```

| 字段 | 必填 | 说明 |
|------|------|------|
| `user_id` | ✅ | 放**外层**，不要只放 payload 里（否则可能落为 `default`） |
| `source` | ✅ | `tool_result` / `user_behavior` / `manual_config` / `conversation` |
| `scene_id` | ❌ | 场景标识，跨场景偏好用 |
| `payload` | ✅ | 原始业务 JSON，交给多源接入模块（3fba60e1）ingestion 清洗 |

**成功响应（`status: accepted`）：**

```json
{
  "status": "accepted",
  "accepted": true,
  "user_id": "demo_user",
  "memory_id": "uuid-...",
  "memory_type": "preference",
  "quality_score": 0.72,
  "fingerprint": "abc123...",
  "updated_existing": false,
  "evicted_memory_id": null,
  "record": {
    "type": "manual_config",
    "content": "用户设置「reply_language」为「中文」",
    "user_id": "demo_user",
    "scene_id": "coding-session",
    "metadata": { "...": "..." }
  }
}
```

**拒绝响应（`status: rejected`）：**

```json
{
  "status": "rejected",
  "accepted": false,
  "reject_code": "low_quality",
  "reasons": ["..."],
  "quality_score": 0.35,
  "record": { "...": "..." }
}
```

**常见 `reject_code`（来自多源接入模块（3fba60e1）ingestion）：**

| reject_code | 含义 |
|-------------|------|
| `low_quality` | 质量分低于阈值（默认 0.6） |
| `duplicate` | TTL 窗口内重复数据 |
| `empty_content` | 清洗后无有效正文 |
| `invalid_source` | source 不合法 |
| `invalid_payload` | payload 结构不对 |

## 十一、常见问题（FAQ）

**Q：写入 `/ingest` 成功，为什么 Milvus 里查不到？**  
A：正常。当前只进了短期记忆；要进 Milvus 需走 `POST /consolidate/{user_id}` → `resolve_and_store()` → cb0aeabe `create_memory()`。

**Q：consolidate 之后 `layers.long` 还有数据？**  
A：`long` 表示**待入库队列**。成功写入 Milvus 后应为 0；若 `memory_policy` 拒绝入库，条目会留在队列中等待重试。

**Q：同一条数据连写两次，短期里几条？**  
A：若 fingerprint 相同 → 1 条（更新）；若 ingestion TTL 去重拒绝 → 0 条新写入（返回 `reject_code=duplicate`）。

**Q：服务重启后短期记忆还在吗？**  
A：不在。当前是内存实现；答辩演示时重新 ingest 即可。

**Q：前端想展示「偏好页」，用哪个接口？**  
A：短期分类结果可用 `GET /short-term/{user_id}?memory_type=preference`；长期偏好与版本历史
可用现有 `GET /preferences/{user_id}`，并通过 `preference_key`、`latest_only` 过滤。
当前长期后端仍是进程内 mock，服务重启会丢失，真实 Milvus 接入后才可按正式库验收。
